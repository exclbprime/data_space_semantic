# TIDE 数据空间项目研究任务与实施要求

本说明完整列出统一场景、四组分工、材料使用、交付成果、验证步骤和推进安排。成员可以在一份文档中了解本项目要求；成果保存平台、命名和分享方式由团队商定。

起始数据、Schema、Shapes、API和身份模板位于 `TIDE_Minimal_Research_Scenario/`。下文表格链接指向实际技术输入；未加完整路径的样例文件名也以该场景包为基准。

## 一 项目目标
在项目方案基础上，明确各组的研究、实现、协作和验证要求。

最终应形成：四类工具研究成果、各组实际实验、统一模型与身份授权、真实Connector数据交换、受限评测、新团队/新资源接入验证，以及可复查的集成演示。

先做局部研究和最小实验，再推进集成；每个阶段可以清楚报告已完成与未完成。失败记录是研究成果，但不能代替目标功能成功运行。

## 二 统一业务场景

### 场景与研究内容
TIDE Research Resource Reuse and Controlled Evaluation。

来源项目发布可共享研究资源，新研究团队发现并申请复用，负责人批准后通过Connector获取。不能直接共享的内部数据由提供方的固定Benchmark Service使用，研究团队只提交规定格式的处理方案并获取允许返回的汇总结果。后续团队可按权限复查来源与版本。

### 业务角色
| 角色 | 示例ID | 职责 |
|---|---|---|
| TIDE共同治理方 | tide-authority | 共同规则、资格和发现机制；不能代替权利人批准企业资源 |
| 来源项目 | source-team | 管理P1，说明来源、权利、许可与版本 |
| 新研究团队 | research-team | 申请和复用P1，提交P3 |
| 受限资源方 | restricted-lab | 管理P2内部数据，执行评测并产生P4 |
| 复查团队 | review-team | 经独立授权查看结果和允许的研究资源 |

四个业务节点各有自己的Connector、IdentityHub、配置与资源边界，共同治理方提供Issuer等服务。A–D是开发分组，不是四个业务节点。学校、企业和团队先用模拟身份，不声称已有真实授权或合作承诺。

### P1至P4
| 产品 | 内容 | 边界 |
|---|---|---|
| P1 Research Resource Package | 合成过程CSV、字典和研究说明 | 获批后通过真实Connector获取 |
| P2 Restricted Benchmark Service | 提供方内部数据和固定评测接口 | 原始记录不返回消费方 |
| P3 Data Processing Recipe | 白名单JSON处理参数 | 不执行用户上传的任意代码 |
| P4 Result and Reuse Record | 汇总指标与版本来源记录 | 按范围授权获取，不附逐条标签 |

### 一次完整协作
1. 来源项目明确权利、许可和可展示范围，C组提供模型，D组验证，A组发布当前合格产品。
2. 新团队发现资源并说明用途；B组记录访问申请，由对应资源负责人批准具体Grant。
3. 验证可信Participant资格、个人当前成员关系、有效Grant及资源/动作/用途范围；通过后才运行EDC协商与交换。
4. 获取P1并核对hash；新团队提交P3，P2接收、执行前和结果领取时检查当前权限。
5. P2运行固定管线并返回P4；复查团队用自己的权限核对来源和版本。
6. 成员退出或授权收回后，停止后续受限访问，包括旧EDR、结果链接或可尝试的后端入口。已合法下载的副本不承诺远程收回。

### 资源与数据约定
通用metadata包含resource_id、participant_id、project_id、title、description、domain、owner、rights_holder、source、license_or_terms、access_level、schema_version、product_version、endpoint_ref、checksum、provenance和维护状态。领域字段放extension，不写死进通用核心。
PUBLIC仅限权利明确可公开资源；PROJECT同时要求资格和具体授权；RESTRICTED以固定服务和限定输出提供。

P1/P2由独立种子生成，各2400条记录，包含温度、流量、控制输入和下一时刻温度标签。示例研究为比较白名单预处理配置在固定ARX基线上的结果，不要求模型分数提升。按时间前70%训练、后30%测试，禁止把target_temp作为输入或用未来数据估计预处理参数。

## 三 共同研究与准备

### 开发分组
| 小组 | 核心工具 | 负责方向 |
|---|---|---|
| A | EDC Connector / MVD研究样例 | 数据交换、服务适配、固定评测和集成环境 |
| B | IdentityHub / Issuer Service | Participant资格、个人映射、资源审批和动态授权 |
| C | Semantic Treehouse | 共同模型、语义规则、版本、合成数据和资源复用 |
| D | ITB / SHACL Validator | 准入验证、全链测试、轻量Portal和演示证据 |

### 每组共同研究的问题
1. 工具在数据空间中解决什么，不解决什么？
2. 输入、输出、标准协议和依赖是什么？
3. 从一个实际请求到结果，经过哪些源码模块？
4. 选了哪个版本，怎样部署、配置和调用？
5. 哪些是工具原生能力，哪些是本组扩展？
6. 如何与其他组对接，字段、规则、身份或接口不一致怎么办？
7. 有哪些成本、许可、维护与真实使用限制？
8. 成功与失败结果怎样重现，证据支持哪些结论？

每组需要一份技术研究说明、一份部署/使用记录、一个阶段Demo或实验，以及相关源码/配置/报告。可合并为一份报告，不要求把每个章节拆成独立文件。文字建议覆盖约5–10页的内容深度。

### 准备工作
确认组内负责人和成员分工；通读统一场景与样例说明；协商共享材料方式和可投入时间；先读官方quickstart并做一次实际调用或部署尝试。现有Teams可用于共读与讨论，代码和大文件保存方式由团队另定。

前两周核对三类角色的真实需求：TIDE运营、项目负责人、资源负责人。若实际仅需公开资料共享，应向导师讨论缩小场景；不能编造多方授权需求。实际日程和例会时间协商确定，不要求成员填写一整套管理表格。

EDC Connector、Control Plane、Data Plane、Catalog、Contract Negotiation、Data Transfer与EDR；从MVD理解组件关系，不把样例直接当生产系统。

### 具体工作
1. 复现两个Participant，梳理一次从Catalog查询到传输完成的原生状态变化，并分析一条实际源码调用链。
2. 把合格的P1资源描述登记为Asset，与B组接入资格和Grant判断；由研究团队完成真实协商与数据获取，核对文件hash。
3. 扩展四业务节点，提供文件包和HTTP两类Resource Adapter，保持个人、项目与资源边界。
4. 实现固定Benchmark Service：接收白名单P3、产生job_id、有限时间轮询、幂等提交、执行和P4输出；不接收任意脚本或模型二进制。
5. 在实际访问路径落实当前授权检查，覆盖Gateway、旧EDR/Data Plane、业务服务和原始存储旁路。与B合作验证退出后不能继续调用。
6. 整理版本、初始化、重置与停止步骤，支持其他成员按说明重建集成环境。

### 验证操作与预期
#### A1 产品发现与发布
**输入/前置：** C确认的P1描述与版本、D当前准入结果、实际Provider与Consumer。

**操作：** 先登记合格metadata为Asset并查询真实Catalog，再分别尝试发布三种错误描述。若发布前由独立准入服务拦截，应记录该拦截与后续Asset未更新的事实。

**预期：** 合格版本可被允许的消费者发现；错误版本不应被发布或静默更新。搜索/Portal不得泄漏不允许展示的字段。仅有Catalog描述不算完成数据传输。

**需要展示：** 采用的描述与规则版本、准入结果、Asset状态与Catalog请求响应。对应TC01。

#### A2 真实协商与P1交换
**输入/前置：** 实际有效资格、当前项目成员与对应READ_DATA Grant；固定P1文件hash。

**操作：** 用Consumer执行Catalog查询、Contract Negotiation、Agreement和Data Transfer，再取得获准内容，计算实际字节SHA-256。

**预期：** 记录工具原生成功状态，传回hash等于清单；不能只调用普通文件服务就声称EDC成功。原生路径与版本以实际采用实现为准，不凭本项目业务API杜撰原生端点。

**需要展示：** 脱敏请求与状态、真实negotiation/agreement/transfer标识、必要EDR记录和hash。对应TC04。

#### A3 输入处理和语义适配
**操作：** 使用C的正确映射与一个单位/字段或版本错误输入，验证是否拒绝，或经明确映射后正确执行。对P3另试未知script、窗口超限和标签作输入。

**预期：** 不兼容输入不静默继续；P3白名单以外的内容不执行。记录映射步骤、修复及对应版本，不能只删掉错误字段后不说明。

**需要展示：** 原始输入、规则/映射、拒绝原因与修复后对照。对应TC05、TC06。

#### A4 P2真实评测与P4出口
**操作：** 提交合法P3、观察QUEUED/RUNNING及终态、领取P4；同时尝试读取原始存储/调试接口，或在返回结果附加records。

**预期：** 固定服务真实运行，不从result-valid-fixture复制分数；P4满足Schema，只返回允许汇总字段及版本引用。P2原始记录与逐条标签不从消费者接口返回。无法计算有效指标时应报错，不伪造0分。

**需要展示：** 新job_id、运行日志、实际P3/P4、服务版本、Schema校验与出口检查。对应TC06。

#### A5 幂等、超时与授权执行
**操作：** 相同主体、相同Idempotency-Key和相同输入重复提交；再用同key改变输入；制造超时。与B收回Grant后，分别重试Gateway、旧EDR/Data Plane、结果链接、后端和原始存储。

**预期：** 相同提交不重复执行，冲突输入明确拒绝；超时有终态和可解释错误。所有后续越权入口在团队确认的失效界限内拒绝；没有批准缓存窗口时不依赖无限缓存。网络隔离也是需要验证的执行边界，不能忽略旁路。

**需要展示：** 执行次数、key/载荷关联、终态、收回时间与各入口请求响应。对应TC07、TC09。

### 与其他组配合
接收C的模型/数据与D的准入结果；接收B的资格与当前授权；向D提供业务API和运行状态。A负责执行点，B负责判定，不能相互假设对方已经拦截。

### 具体工作
1. 确认与EDC兼容的身份版本和实际Credential机制，研究签发、存储、呈现、验证和subject绑定。

6. 测试未获批、到期、不信任Issuer、篡改proof、收回Grant与成员退出；分别说明VC状态管理和业务Grant撤销做到了什么。

### 验证操作与预期
#### B1 Credential真实与可信
**输入：** B通过实际工具签发的测试Credential/VP；另备不信任Issuer、到期、被篡改proof的独立案例。

**操作：** 通过冻结的IdentityHub/DCP等实际链验证，检查签名/证明、Issuer、subject和有效期。启动模板仅用于理解字段，不能作为成功身份。

**预期：** 合法资格通过，其余按准确原因拒绝。仅JSON结构通过不算真实身份验证。

**需要展示：** 签发/呈现/验证路径、版本、脱敏身份材料和原始成功/失败判定。对应TC02。

#### B2 资格与具体资源批准分离
**操作：** 有效项目成员在无Grant时访问P1；由合法资源负责人批准后重试；再尝试由申请人自批，或拿P1 Grant调用P2/P4。

**预期：** 未获批拒绝、合法批准后允许、自批拒绝、超出资源/动作/用途范围拒绝。TIDE运营身份不能默认覆盖资源负责人意见。

**需要展示：** 同主体和资源的申请、负责人身份、Grant状态与前后请求；拒绝原因必须匹配本次错误，不是任意403。对应TC02。

#### B3 个人、团队和项目隔离
**操作：** 对比同校不同项目成员；对比同团队一个在籍成员和一个已退出成员；尝试修改前端传入的team/role字段。

**预期：** 服务端根据可信个人映射和当前关系判断。其他项目与退出个人不能借有效团队节点或团队Grant访问；自报role不应提升权限。

**需要展示：** 测试主体、服务端映射与范围、允许和拒绝记录。对应TC03。

#### B4 Grant到期、收回与异步任务
**操作：** 分别测试期限已到、ACTIVE变REVOKED、个人退出；任务处于QUEUED和RUNNING时改变权限；尝试执行和结果领取。

**预期：** 日期检查使用服务端当前时间，不等后台改状态才生效；待执行任务取消或拒绝执行，收回后不能领取受限结果。已经合法下载副本不纳入“远程收回”承诺。

**需要展示：** 时间/状态变化、同请求重试、任务状态及结果领取判定。与A共同对应TC07。

#### B5 判定服务故障
**操作：** 在原本合法请求期间使当前授权服务不可用，再恢复。

**预期：** 不因超时/异常而默认允许；返回明确服务故障与拒绝执行的结果。恢复后按当前状态重试，不能复用过期允许缓存。

**需要展示：** 故障/恢复方法、错误响应与A没有放行的证据。对应TC09。

### 与其他组配合
向A提供可信判定和执行点对接条件，向D提供测试账户、签发/批准/收回的可复现操作；私钥和真实token不交给普通成员或浏览器。

| metadata/p1-missing-rights.jsonld | 同上 | 不合格 | 缺rights_holder |
| metadata/p1-missing-source.jsonld | 同上 | 不合格 | 缺source |
| metadata/p1-invalid-access.jsonld | 同上 | 不合格 | access_level不在PUBLIC/PROJECT/RESTRICTED中 |
| examples/recipe-valid.json | schemas/recipe.schema.json | 合格 | 白名单参数、合法窗口/lag与版本 |
| examples/recipe-invalid.json | 同上 | 不合格 | 多余script及超限窗口 |
| examples/result-valid-fixture.json | schemas/result.schema.json | 结构合格 | 只包含允许字段；指标本身为示例值 |
| examples/result-invalid-leak.json | 同上 | 不合格 | 添加了不允许的records，可能泄漏逐条数据 |

不要把“预期不合格的样例被拒绝”写成实验失败；那正是负向测试应得到的结果。

## 十 整体完成标准

| 用例 | 主要负责 | 必须看到的行为 |
|---|---|---|
| TC01 发布准入 | C/D/A | 合格可发布，缺字段/非法取值不发布 |
| TC02 资格与审批分离 | B/A/D | 有资格未获批拒绝，合法批准后允许；无效资格、自批拒绝 |
| TC03 项目/个人隔离 | B/A/D | 跨项目、退出个人不能借团队权限 |
| TC04 真实P1交换 | A/C/D | EDC原生流程成功，实际内容hash匹配 |
| TC05 语义与版本 | C/A/D | 错误显式拒绝或转换，v1/v2不静默混用 |
| TC06 受限服务 | A/C/D/B | 真实P3→P2→P4；拒绝非法输入，不泄漏原始记录 |
| TC07 退出和旧入口 | B/A/D | 收回后后续旧EDR/链接/后端/存储访问拒绝；异步结果也受控 |
| TC08 复现与复查 | C/A/B/D | 固定输入指标一致，复查者按独立权限访问 |
| TC09 故障与幂等 | A/B/D | 不可用不放行，重复不重复执行，冲突/超时有明确结果 |
| TC10 新团队接入 | 全组，D组织 | 新DID/配置/授权，先拒绝后成功，核心源码无需修改 |
| TC11 新资源接入 | C/A/D | 新领域扩展准入与真实交换，核心保持复用 |

完整原型需说明并通过全部TC；TC04、TC06、TC07、TC10不可由静态文件或口头解释替代。单组初期实验完成不等于全系统完成。

### 结果与证据如何记录
- 正向请求实际达到预期，记录通过。
- 负向输入被系统按预期原因拒绝，也记录通过。
- 行为不符合预期，记录未通过及责任组、修复与重跑结果。
- 非预期服务故障、外部阻塞、未运行分别说明，不记成通过。
- 故意故障注入要求“不放行并返回503”时，确实如此属于该故障用例通过。

每组提供与本人任务相关的原始材料；D关联跨组结果。建议记录工具版本、输入、时间、测试主体、agreement/transfer/job/session等标识、规则/文件hash及脱敏输出。形式可灵活，不强制JSON Manifest或固定路径。

复验应能区分前后结果，不能覆盖失败记录后声称从未出现。截图和录屏辅助解释，代码/规则/配置、原始报告与复现步骤仍需可取得。

## 十二 最终报告与演示

报告可包括：问题与场景、工具链、四组研究与实现、原生能力与扩展、集成实验、测试与复用、成本/限制、个人贡献和下一步。不同组的报告可汇总成一份，避免重复介绍概念。

对比矩阵建议维度：架构位置、输入输出、采用版本、部署成本、实际能力、自主扩展、不负责什么、许可与限制、实验结论。每个结论附官方文档/源码或实际实验依据。

15–20分钟演示可按“发现资源→申请→批准→真实交换→受限评测→复查→撤权后拒绝→新团队接入”组织。PPT或录屏可辅助，不能替代可重跑的实现和原始结果。

## 十三 责任与实现边界

- 资源负责人决定具体产品授权；TIDE运营或共同Issuer不能替权利人处分企业/课题组数据。成员资格、个人登录和具体Grant是不同条件。
- 所有节点先用模拟身份，P1/P2为本届新建合成数据，不声称已有真实企业授权或生产数据；实际试点需另行确认权利、用途和范围。
- 本包的example.invalid地址与DID是占位，未签名claims没有有效proof/信任链；Grant样例不表示真实批准；P4样例指标是虚构结构示例，不是计算结果。
- Schema/SHACL合格只支持相应内容符合性结论，不等于身份真实、具体访问获准、法律合规或系统验收通过。
- P2在教学材料中可见，运行原型仍需限制在提供方；消费者出口不得返回原始记录与逐条标签。不接收任意用户代码，不在可分享报告中泄露真实密钥或敏感信息。
- 原型与MVD研究样例不是生产系统；工具版本与容量需实际确认。已合法下载的副本不能承诺远程收回，使用条件还需责任约定配合。
- 第一阶段不引入完整项目管理、学校SSO、真实报名信息、任意代码执行或跨领域自动通用Benchmark。不同领域可复用资源协作框架，业务计算服务需要另行设计。

工具失败可以形成研究记录，但不能替代功能运行完成。报告如实区分实际运行、模拟、未运行与未完成。重要技术结论附采用版本、源码或官方材料依据。
