# C 组语义互操作任务清单

## 核心目标

让另一支研究团队按欧洲数据目录的共同约定发现并复用 TIDE 资源。第一步是让它读懂 **P1 可申请的数据集及其文件**和 **P2 可调用的评测服务**，能判断谁发布、适用什么条款、可获取哪个版本。随后要能从评测结果 P4 查回实际使用的处理方案 P3、数据和算法版本。

启动包把 P1、P2 都标成 `tide:ResearchResource`，标题也都映射到占位词汇 `tide:title`。第一阶段用这两个样例检验初版模型。另一套目录能否用标准词汇找到 P1 的分发文件，同时识别 P2 只提供服务？这决定要复用哪些标准概念、哪些含义需要 TIDE 自己定义。[P1 描述](TIDE_Minimal_Research_Scenario/metadata/p1-valid.jsonld) · [P2 描述](TIDE_Minimal_Research_Scenario/metadata/p2-valid.jsonld)

## 第 1–2 周　确定语义口径并交付 P1 初版

01、02 和 05 可以并行开始。核对时在末列附产物、Issue 或 PR 链接及结论。AI 可整理候选映射、定位源码和运行样例。业务定义、可展示范围及跨组约定以实际确认记录为准。

| 任务 | 交付物 | 完成判据 | 进度／证据 |
| --- | --- | --- | --- |
| 01 界定跨目录使用场景 | 一页用例，列出谁发布、谁查询、允许看什么、预期读到什么 | 以“新团队查找可申请的工业过程数据”为例，写出选中 P1、区分 P2 的依据。与 TIDE 运营、项目方和资源方核对需求，并注明目标目录是否已确定 | 待确认 |
| 02 选定欧洲规范基线 | DCAT 和欧洲应用规范 DCAT-AP 的试验版本、适用条款及选版理由 | 能说明所选版本如何对应报告中的 DCAT 2.0 要求，以及哪些约束来自欧洲目录、哪些由 TIDE 添加。提案中的 EOSC 协同目标与已取得的伙伴要求分别标注来源 | 待确认 |
| 03 建立共同模型和字段映射 | 一份 TIDE 应用规范初稿，附 P1 数据集、CSV 分发和 P2 服务的目录样例。逐字段写明标准词汇标识符、值类型、必填条件、展示范围及本地扩展 | 从样例读出发布者、权利人、适用条款和获取方式。核对 `license_or_terms` 能定位条款文本，并说明温度、流量单位如何在工业扩展中表达 | 待评审 |
| 04 约定标识、版本和词汇地址 | 一个产品升级前后的对照，列明 `resource_id`、RDF 节点 `@id`、产品版本、规则版本和词汇地址 | 用例子确认 A 更新哪个目录条目、B 的原授权适用于哪个资源，以及 D 应选哪版规则。核对写死为 `1.0.0` 的 P3 版本约束如何处理升级，记录正式词汇地址或替换占位地址的条件 | 待确认 |
| 05 确定 P1 交付范围和哈希 | 实际交付文件、数据字典及逐文件 SHA-256 清单。与 A 组约定首批传 CSV 还是整包 | 在工作副本按记录的种子重生成至少 2,000 条数据，核对列、单位、时间顺序和 CSV 哈希。现有描述的 `checksum` 指向 CSV。若交整包，分别按整包和 CSV 的原始字节重算哈希 | 待复核 |
| 06 在 Semantic Treehouse 建立初版模型 | 一次真实实例的建模或导入记录，附工具版本、输入和结果 | 选 03 中一个字段，对照标准定义与实例中的模型节点。操作成功附模型版本标识，受阻则记下失败步骤及影响 | 待实测 |
| 07 验证 P1 的正例和反例 | 同版 JSON Schema、SHACL、业务检查说明和逐例报告 | 合法 P1 通过。缺权利人、缺来源、非法访问级别分别触发预期错误。核对 SHACL 命中的资源节点，并对实际文件重算哈希 | 待复跑 |
| 08 向 A、D 交接同一版材料 | 向 A 交付目录映射、可展示字段和文件清单，向 D 交付同版描述、规则、样例和预期结果 | A 能确定将发布什么、交付哪个文件并复核哈希。D 独立复跑 07。两份记录指向同一产品版本和规则版本 | 待交接 |

**近期跨组事项。** A 组希望在 **11 月 20 日前**收到首轮反馈。先答复新数据交付（C13）、升级是否换资源 ID（C14）和正式词汇地址（C15），再将已确认的约定用于任务 04、05、08。[A 组需要 C 组答复的问题及要点](TIDE_A_to_C_Questions.md)

## 后续任务　验证真实交换、评测与跨领域复用

| 阶段与任务 | 交付物 | 完成判据 | 进度／证据 |
| --- | --- | --- | --- |
| 09 第 3–4 周　验证模型如何生成发布规则 | 实际模型版本、一条从操作到输出的源码路径、工具导出或转换结果、手工补写项及 D 的准入报告 | 选一条必填约束，从模型字段追到对应规则，再用反例查到 D 的错误路径。A 能据报告识别可发布的版本（TC01） | 待联调 |
| 10 第 3–6 周　独立读取真实目录 | A 发布的目录条目、所选 DCAT-AP 版本的校验报告及独立查询结果 | 用标准词汇查询实际目录或其标准导出，答出 01 中 P1 的发布者、条款、获取方式和版本。记录本地校验结果，有实际欧洲伙伴联测时另附其读取结果 | 待联调 |
| 11 第 5–6 周　核对真实传输的文件 | 获准的 EDC 传输 ID、接收文件及 05 的清单 | 从传输记录定位该次交付，在接收端计算 SHA-256，与该产品版本清单中的对应文件一致（TC04） | 待联调 |
| 12 第 7–8 周　区分 P2 服务和评测数据 | 本届 P2 数据的生成记录、字典，以及服务说明和内部 CSV 各自的版本及哈希 | P1/P2 各至少 2,000 条，种子和工况独立。分别重算 P2 描述所指的服务说明、P4 的 `p2_sha256` 所指的 CSV，并核对 `benchmark_version` 对应的服务版本 | 待复核 |
| 13 第 7–8 周　固定 P3 的计算含义 | 与 A 确认是否仅用 P2 计算，用带缺失值、跨时间切分点的短序列写出预期特征、标签和有效样本数 | 按时间 70/30 切分，训练均值只取训练段，平滑和滞后只用预测时已知的观测，剔除跨界训练标签。核对特征顺序、`recipe_sha256` 及 `valid_ratio` 分母。含 `script` 或标签作特征的 P3 应被拒绝（TC05、TC06） | 待确认 |
| 14 第 7–8 周　追溯 P4 并复现结果 | 固定输入和环境的两次真实作业，附 P3、P4、版本记录及一个含逐条 `records` 的输出反例 | 从两个作业 ID 查回数据、处理方案和算法版本。样本数一致，MAE 差在事先约定的容差内。复查者凭独立授权领取汇总结果，含逐条记录的输出被拦截（TC06、TC08） | 待联调 |
| 15 第 7–8 周　验证 v1/v2 兼容性 | 一项单位或必填字段变更、旧新输入、两版规则和预期结果 | 交叉运行四种组合。对可转换的单位核对转换值，对不兼容输入核对拒绝原因，旧版本仍可复查（TC05） | 待复跑 |
| 16 第 9–10 周　检验第二领域能否复用核心 | 一份第二领域资源包（如文档）、对应扩展、正反例及交换记录 | 对照模型差异，核对通用核心的复用。D 接受合法描述并拒绝非法扩展，A 完成真实交换，接收哈希匹配（TC11） | 待联调 |
| 17 第 11–12 周　独立复跑与交付 | 一份索引，链接模型、规则、输入版本、运行步骤和前述证据 | 由未参与该次运行的人从索引重建一次演示，记录实际复现的结果、差异及仍需处理的问题 | 待复跑 |
